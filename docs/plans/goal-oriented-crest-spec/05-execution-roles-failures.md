# Workstream 5: Execution Provenance, Specialized Roles, and Failure Triage

Status: **Draft**  
Depends on: WS4; uses WS1–WS3  
Enables: WS6, WS7, WS8  
Original scope: Workstreams 8, 12, and 13

## Objective

Record how an external host executed every generation attempt, shape work for specialized responsibilities, and route failures according to their actual cause instead of treating all rejection as a prompt/model retry.

crest-spec remains provider- and host-independent. Hosts execute agents; crest-spec defines, validates, persists, and exposes the attempt contract.

## Requirements

### Execution provenance

- Record host name/version, provider, exact model, inference settings, system instructions, tools, permissions, agent configuration, role, templates, context hash, retry ancestry, timestamps, candidate files/hashes, validation outcome, goal progress, failure, and disposition.
- Link execution to session, persisted plan operation, goals/capability, resource, context manifest, candidate snapshots, validations, evidence, retry chain, and final accepted file versions/commit when reported.
- Snapshot rejected candidates so later retries cannot erase diagnostic evidence.
- Store redacted metadata only; credentials, bearer tokens, secret environment values, and private tool arguments are prohibited.

### Roles

Support the initial closed role registry:

- `project_goal_analyst`
- `planner`
- `resource_implementer`
- `integration_implementer`
- `test_generator`
- `behavioral_witness_author`
- `failure_triage`
- `architecture_reviewer`
- `security_reviewer`
- `minimal_diff_repair`
- `project_completion_reviewer`

Each role has a versioned context policy, permitted lifecycle actions, expected output kind, and handoff rules. Roles do not receive authority to accept their own output or override mechanical gates.

### Failure classification

Persist the requested taxonomy:

- missing project intent
- missing context
- incorrect context selection
- stale context
- context truncation
- ambiguous resource contract
- architectural inconsistency
- implementation error
- integration error
- invalid validation
- behavioral theater
- tool failure
- host failure
- model failure
- unsupported project pattern

Every classification includes evidence, classifier origin, confidence for advisory classifications, corrective action, resolution, and links to affected goals/resources/attempts/validations.

## Versioned host protocol

### Start

`spec/execution_start` accepts the `attempt_id` returned by `spec/context` plus:

- protocol version
- host/provider/model identity
- role
- redacted inference and agent configuration
- system instruction content/hash
- available tool names and permission summary
- template hashes
- start timestamp or server-time request

The engine verifies that the context hash and role match the prepared attempt. Only one active execution may own an attempt.

### Commit

`spec/commit` requires `attempt_id`; session/resource are derived and any duplicated caller values must match. It accepts candidate files, notes, model usage/duration where known, and host completion metadata. The engine:

1. validates attempt/execution state;
2. snapshots every candidate file into content-addressed SQLite blobs;
3. writes candidate files through existing file safeguards;
4. executes the appropriate validations;
5. records validation and goal consequences;
6. atomically marks accepted/rejected disposition and session-resource state.

### Completion and cancellation

Hosts can explicitly record cancelled, crashed, or timed-out executions that produced no candidate. Server recovery marks abandoned active attempts after an explicit policy threshold; it does not infer model failure without evidence.

## Role and handoff model

- Plan operations carry the recommended initial role.
- A retry may retain the role or create a persisted handoff to another role.
- Handoffs include reason, source attempt, target role, expected corrective outcome, and relevant failure classification.
- Role-shaped context is generated by WS4 policy variants, not by separate truth stores.
- Reviews and triage produce advisory records; acceptance remains tied to deterministic validation/evidence.

## Failure routing

Default corrective actions are deterministic and configurable:

| Failure class | Default next action |
|---|---|
| Missing intent / ambiguous contract | Block generation and request specification repair |
| Missing/incorrect/stale/truncated context | Rebuild context with a recorded policy/budget change |
| Architectural inconsistency | Re-plan or require architecture review/spec amendment |
| Implementation error | Minimal-diff repair with prior candidate and raw failure |
| Integration error | Integration implementer with consumers and wave evidence |
| Invalid validation | Block implementation retry; repair the validation definition |
| Behavioral theater | Re-author witness/check; never regenerate implementation by default |
| Tool/host failure | Retry infrastructure after health confirmation; preserve candidate if any |
| Model failure | Retry or select another configured host/model through the host |
| Unsupported pattern | Escalate to human and propose a resource/schema extension |

Advisory agents may propose a classification, but the record must cite persisted evidence. Human overrides append a new decision and never rewrite history.

## Persistence ownership

WS5 owns:

- execution manifests and lifecycle events
- redacted inference/tool/permission/agent configuration
- candidate file sets and content-blob references
- roles, role policy versions, assignments, and handoffs
- failure classifications, evidence links, corrective actions, and resolutions
- retry/execution ancestry and final dispositions
- optional reported git commit references linked after acceptance

Store configuration as structured normalized fields where it drives queries and canonical JSON only for provider-specific settings. Canonical JSON must be hashed and redacted before persistence.

## Tasks

### WS5-01 — Define the attempt/execution state machine

- Specify states from context-prepared through executing, candidate-submitted, validating, accepted/rejected/cancelled/failed.
- Define valid transitions, idempotency keys, concurrency ownership, timeouts, and recovery.
- Version the host protocol and publish capability negotiation through MCP initialize metadata.

Acceptance: invalid transitions fail closed without changing session, candidate, or resource state.

### WS5-02 — Persist execution and candidates

- Add focused migrations, queries, repositories, and transactional operations.
- Implement redaction and canonical hashing.
- Snapshot candidates before mutable working-tree writes.
- Link final accepted generated-file rows and optional host-reported commit hashes.

Acceptance: accepted and rejected candidate file contents remain reconstructable and hash-verifiable.

### WS5-03 — Implement the versioned MCP contract

- Add `spec/execution_start`, cancellation/failure reporting, attempt-aware `spec/commit`, and attempt inspection.
- Require context/execution manifest relationships for all new protocol attempts.
- Return structured state conflicts and recovery guidance.

Acceptance: no new commit can be accepted without a prepared context and execution manifest.

### WS5-04 — Add roles and handoffs

- Implement the closed role registry and policy versions.
- Associate plan operations and attempts with roles.
- Validate role-appropriate lifecycle actions and output kinds.
- Persist explicit handoffs and render role-shaped context through WS4.

Acceptance: a failed resource attempt can hand off to minimal-diff repair or integration implementation without losing provenance.

### WS5-05 — Classify and route failures

- Implement deterministic classifications from engine-known signals.
- Add advisory classification submission with evidence validation.
- Apply default corrective actions and block inappropriate retries.
- Persist resolution and eventual successful attempt links.

Acceptance: an invalid validation or missing intent cannot enter a blind model retry loop.

### WS5-06 — Update hosts and inspection

- Update bundled Claude Code workflows, generated OpenCode agents, host docs, and examples atomically with the protocol.
- Add execution, role, handoff, failure, and retry-chain APIs and dashboard views through WS8.
- Add comparison by host, model, template, context policy, role, and retry.

Acceptance: both reference hosts complete a generation/retry flow and produce equivalent required provenance.

## Test plan

- State-machine table tests for every valid/invalid transition, duplicate message, timeout, cancellation, and recovery.
- Store tests for transaction rollback, candidate reconstruction, retry chains, and content deduplication.
- Redaction tests using nested provider settings, environment-like values, headers, tool arguments, and malicious key casing.
- Protocol tests for missing/incorrect context hash, duplicate execution owner, mismatched resource, and legacy call rejection.
- Role tests for assignment, context policy, prohibited action, handoff, and acceptance separation.
- Failure-routing tests for every category and human override history.
- Host adapter contract tests against a fake MCP server.
- Dashboard/API comparison tests across host/model/role/retry variants.

## Compatibility and rollout

The new host protocol is released with a declared version and capability discovery. Bundled adapters are updated in the same change. Legacy historical generations remain readable and labeled `legacy`; they are not assigned invented context, execution, role, or candidate provenance.

During development only, a feature flag may permit the old commit signature for migration tests. It must be removed or disabled by default before the workstream exit gate.

## Exit gate

- Every new generation has an immutable context, execution, candidate, and disposition chain.
- Specialized roles and explicit handoffs are operational through reference hosts.
- Failures route to appropriate corrective actions and block invalid retries.
- Execution and failure comparisons are inspectable without provider coupling.
